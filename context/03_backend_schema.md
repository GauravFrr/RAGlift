# Backend & Data Schema
## Production RAG Starter Kit

Intentionally lightweight — this is a starter kit, not a multi-tenant production system. No relational DB is required; ChromaDB's own metadata store plus flat files cover everything.

### 1. ChromaDB Collection: `chunks`
| Field | Type | Notes |
|---|---|---|
| `id` | string | `{doc_id}_{chunk_index}` |
| `embedding` | vector | generated by configured `EmbeddingProvider` |
| `document` | string | raw chunk text (also used by BM25) |
| `metadata.doc_id` | string | source document identifier |
| `metadata.chunk_index` | int | position within source document |
| `metadata.source_path` | string | original file path/name |
| `metadata.ingested_at` | ISO timestamp | for debugging/traceability |

### 2. BM25 Index
- Built in-memory from the same chunk set at ingestion time (`rank_bm25`)
- Persisted to disk as a pickle (`data/bm25_index.pkl`) so it survives restarts without re-ingesting
- Keyed by the same `id` as the ChromaDB entries so fusion can match results

### 3. Ingestion Log (`data/ingestion_log.jsonl`)
Flat append-only log, one JSON line per ingested document — avoids needing a real DB while still giving buyers an audit trail:
```json
{"doc_id": "...", "source_path": "...", "chunk_count": 12, "ingested_at": "..."}
```

### 4. Eval Query Set (`eval/sample_queries.json`)
```json
[
  {
    "query": "How do I authenticate API requests?",
    "relevant_chunk_ids": ["auth_guide_0", "auth_guide_1"]
  }
]
```
Buyers replace this file with their own labeled queries to measure recall on their own corpus.

### 5. Why No Postgres/SQL Layer
Keeping the kit dependency-light was a deliberate choice — fewer moving parts for a buyer to set up means faster time-to-first-query. If a buyer needs multi-user access control, audit history, or a management UI, that's explicitly flagged in the README as an extension point, not something the kit ships with.
